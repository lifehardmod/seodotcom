# seodotcom SEO 점검 — 2026-09-28

점검 대상은 `lifehardmod/seodotcom`, `master@36b6517`, 운영 사이트 `https://www.seojuwon.work/`이다. 로컬 소스와 프로덕션 빌드, 실제 배포 응답, 브라우저 렌더링, Lighthouse, Vercel 프로젝트 설정을 함께 확인했다.

**검색 수집을 막는 전면적인 장애는 없지만, 하위 페이지 canonical·도메인·페이지 제목의 정리가 우선이다.** Lighthouse SEO 점수는 검사하는 기본 항목의 통과 여부이며, 페이지 사이의 canonical 의미나 콘텐츠 중복까지 보장하지 않는다.

[전체 12개 페이지의 모바일·데스크톱 측정표와 원본 근거](seo-audit-2026-09-28-metrics.md)를 함께 남겼다. 모바일 홈은 55~96점, RABBIT 상세는 34~35점으로 측정됐다. 홈의 큰 편차와 실험실 측정의 한계를 부록에 명시했다.

## 점검 범위와 정상 항목

- UI 경로 12개를 운영 환경과 로컬 프로덕션 서버에서 각각 GET 검사했다. 모두 HTTP 200이며, 제목·설명·canonical 결과가 일치한다.
- 빌드에서 UI 경로 12개 모두 정적 생성(`○`)을 확인했다. `/api/feedback`은 서버 기능(`ƒ`)으로 남아 있는 Next.js 앱이며 `output: 'export'` 사이트는 아니다.
- `npm run build` 성공: 컴파일, ESLint, TypeScript 검사와 정적 페이지 생성 완료. `npm run lint`도 성공.
- `robots.txt`와 `sitemap.xml`은 HTTP 200이며 구문을 읽을 수 있다. robots는 전체 경로를 허용한다.
- 존재하지 않는 경로는 실제 HTTP 404와 `noindex`를 반환한다. `/programming/`은 `/programming`으로 정규화된다.
- 모든 페이지에 `lang="ko"`, title, description, viewport, canonical이 있다. 최초 HTML의 이미지에는 모두 alt 속성이 있다.
- 12개 경로에서 JavaScript 활성/비활성 두 조건을 각각 검사하고 390px·1440px 화면을 확인했다. 관측 구간에 페이지 전체의 가로 넘침, uncaught JavaScript 오류, 로딩 완료된 이미지의 깨짐은 없었다. 모든 숨겨진 탭·모달·아래쪽 lazy image의 조합까지 통과했다는 뜻은 아니다.
- HTML에 Google 소유권 확인 메타 태그가 있다. 태그 존재 자체가 Search Console 등록 완료를 의미하지는 않는다.

## 우선순위 1: 페이지 대표 주소와 도메인

### 1. 하위 페이지 11개가 모두 홈페이지를 canonical로 지정

`src/app/layout.tsx:17`의 `https://seojuwon.work`가 하위 페이지에 그대로 상속된다. 예를 들어 `/programming/rabbit`, `/programming/mimo`, `/resume`이 각자의 URL 대신 홈페이지를 대표 주소로 출력한다.

canonical은 중복되거나 매우 비슷한 콘텐츠의 대표 URL을 지정하는 강한 신호다. 서로 다른 프로젝트와 이력서를 홈페이지로 묶는 현재 설정은 검색엔진에 잘못된 통합 신호를 보낸다. Google이 실제로 이를 수용했는지는 Search Console의 Google 선택 canonical로 확인해야 한다. 이 설정만으로 하위 페이지가 반드시 색인에서 제외됐다고 단정하지 않는다. [Google canonical 지침](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

조치: 페이지별로 자기 자신을 가리키는 canonical을 선언한다. 예시는 `https://www.seojuwon.work/programming/rabbit`이다. 추적 쿼리가 붙은 주소도 같은 깨끗한 경로를 대표 주소로 사용한다.

### 2. Vercel 운영 도메인과 SEO URL이 불일치

실제 응답과 Vercel 도메인 API 모두 다음 상태를 확인했다.

```text
https://seojuwon.work/programming/rabbit
  --307--> https://www.seojuwon.work/programming/rabbit --200

https://seodotcom.vercel.app/programming/rabbit
  --308--> https://seojuwon.work/programming/rabbit
  --307--> https://www.seojuwon.work/programming/rabbit --200
```

canonical, sitemap URL, robots의 sitemap 주소, OG 이미지 URL은 `www` 없는 도메인을 사용한다. `vercel.json`도 Vercel 기본 도메인을 `www` 없는 주소로 보낸다.

조치: 이미 실제 콘텐츠를 제공하는 `https://www.seojuwon.work`를 기준으로 통일한다. Vercel의 apex→www 리다이렉트를 영구 이전 의도에 맞는 308/301로 명시하고, 기본 Vercel 도메인도 www로 바로 보내 중간 이동을 줄인다. 경로·쿼리가 보존되는지 다시 확인한다. 반대로 apex를 주 도메인으로 선택할 수도 있지만, 코드와 배포 양쪽을 한 번에 맞춰야 한다.

근거: `src/app/layout.tsx:17`, `src/app/sitemap.ts:5`, `src/app/robots.ts:9`, `vercel.json:11`, Vercel `seodotcom` 도메인 설정.

### 3. 12개 페이지의 title과 description이 동일

모든 title은 `SeoJuWon`, description은 같은 포트폴리오 소개다. RABBIT, MIMO, 이력서를 검색 결과에서 구분할 정보가 부족하다. Google도 각 페이지의 내용을 설명하는 구별되는 제목을 권장한다. [Google 제목 지침](https://developers.google.com/search/docs/appearance/title-link)

조치 예시:

| 경로 | 제목 예시 |
| --- | --- |
| `/` | 서주원 · 프론트엔드 개발자 포트폴리오 |
| `/programming` | 개발 프로젝트 · 서주원 |
| `/programming/rabbit` | RABBIT · NFT 차용증 서비스 개발 · 서주원 |
| `/programming/mimo` | MIMO · 모임 관리 서비스 개발 · 서주원 |
| `/resume` | 이력서 · 프론트엔드 개발자 서주원 |

각 페이지의 역할·기술·실제 성과를 담은 description과 OG title/description도 함께 작성한다. Next.js 서버 페이지에서 정적 `metadata`를 내보내면 현재 정적 생성 방식을 유지할 수 있다. [Next.js 15 Metadata API](https://nextjs.org/docs/15/app/api-reference/functions/generate-metadata)

## 우선순위 2: 사이트맵·내부 링크·콘텐츠

### 4. 사이트맵 3개, 홈페이지에서 도달 가능한 페이지 5개

사이트맵은 `NAV_ITEMS`에서 만들어 `/`, `/programming`, `/resume`만 포함한다. 공개 핵심 프로젝트인 `/programming/rabbit`, `/programming/mimo`가 빠져 있다. 내부 링크가 있어 발견은 가능하지만 사이트맵과 실제 공개 페이지 집합이 일치하지 않는다.

사이트맵에서 빠진 경로는 9개다. 전부 무조건 추가할 대상은 아니다. 먼저 완성된 공개 페이지와 숨길 페이지를 구분해야 한다. `lastModified: new Date()`는 콘텐츠 수정일이 아니라 빌드 시각을 기록하므로 실제 내용 변경일을 쓰거나 정확한 날짜가 없으면 생략한다. Google은 sitemap의 `priority`와 `changefreq` 값을 사용하지 않는다. [Google 사이트맵 지침](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

홈에서 일반 HTML 링크를 따라 도달한 경로:

```text
/, /programming, /programming/mimo, /programming/rabbit, /resume
```

홈에서 도달하지 못한 경로:

```text
/blog, /programming/classon, /programming/duduji,
/ux, /ux/a7m3, /ux/assembly, /ux/rabbit
```

`src/constant/nav.ts:13`에서 UX와 Blog 메뉴가 주석 처리되어 있다. 숨김이 의도라면 그 자체가 버그는 아니지만, 페이지는 모두 200과 `index, follow`로 열려 있다. 공개하려는 페이지에는 내부 링크를 연결하고, 준비 중인 페이지에는 `noindex, follow` 또는 적절한 제거/이동 정책을 정한다.

### 5. UX의 A7M3 카드가 두더지 게임으로 이동

`src/components/common/Card.tsx:27`은 공용 카드의 `id === 3`을 모두 `https://duduji.site`로 바꾼다. `/ux`의 A7M3도 id 3이므로 `/ux/a7m3` 대신 게임으로 이동한다. 운영 HTML에서도 이 링크를 확인했다.

조치: 개별 카드 데이터에 외부 URL을 넣고 공용 컴포넌트는 전달받은 URL을 그대로 사용한다.

### 6. 미완성·이미지 중심 페이지의 색인 정책

`<main>` 내 DOM 텍스트 기준 `/programming/duduji`는 6자, `/blog`는 13자, `/ux/a7m3`는 0자, `/ux/assembly`는 34자다. 글자 수는 검색 품질의 합격선이 아니며, 여기서는 제목만 있거나 설명 대부분이 이미지에 있다는 근거다.

- `/blog`: “개발중입니다.”와 미니게임. 준비 중이면 `noindex` 대상.
- `/programming/duduji`: 제목만 존재. 외부 완성 사이트로 보낼지, 실제 개발 사례를 채울지 결정.
- `/ux/a7m3`: H1과 본문 설명이 없고 이미지 11개로 구성. 프로젝트 목적, 문제, 설계 판단, 결과를 HTML 텍스트로 보강. 일부 alt는 `4`, `5`처럼 숫자뿐이다. 근거: `src/app/ux/a7m3/page.tsx:10`.
- `/ux/rabbit`: `RabbitAccordion.tsx:23,47`에서 선택한 탭 하나만 렌더링한다. 디자인 시스템·UI·회고의 본문은 초기 DOM에 없다. 검색 대상 본문은 정적으로 렌더링하고 탭은 표시 방식만 바꾸거나 독립 URL을 제공한다. Google은 보통 버튼 클릭으로 새 콘텐츠를 불러오지 않는다. [JavaScript SEO 지침](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)

### 7. 프로젝트 GitHub 링크 2개가 비로그인 방문자에게 404

`https://github.com/lifehardmod/RABBIT`, `https://github.com/lifehardmod/MIMO`에서 404를 확인했다. 비공개 저장소인지 삭제·이름 변경 때문인지는 비로그인 응답만으로 구분할 수 없다. 채용 담당자 등 일반 방문자가 볼 수 있는 링크로 정리하거나 비공개임을 안내한다.

근거: `src/app/programming/rabbit/page.tsx:64`, `src/app/programming/mimo/page.tsx:82`. 본인 프로필, SSAFY, 두더지 사이트 링크는 최종 200.

## 성능·모바일·접근성

Lighthouse 측정표와 재측정 결과는 별도 측정 부록에 기록한다. 12개 경로를 모바일·데스크톱 각각 측정했다. 모바일은 Lighthouse 기본 simulated throttling(약 1.6 Mbps, CPU 4배 감속), 데스크톱은 공식 desktop config를 사용했다. 기기 설정은 결과 JSON의 `configSettings.formFactor`로 검증했다.

이는 해당 시점의 **실험실 측정**이다. 실제 사용자 28일 데이터나 Search Console Core Web Vitals 합격 판정이 아니다. TBT 역시 실제 사용자 INP를 대신하지 않는다. [Core Web Vitals와 측정 구분](https://web.dev/articles/vitals)

확인한 개선 대상:

1. **공통 폰트 2.06 MB.** 모든 경로에서 `PretendardVariable.woff2`를 요청한다. 한글 서브셋/분할 전송, 필요한 글리프와 굵기 축소를 검토한다. `next/font/local`을 쓰더라도 원본 파일의 크기 자체가 자동으로 줄어드는 것은 아니다. 근거: `src/styles/globals.css:44`와 실제 네트워크 기록.
2. **첫 화면 동영상.** 홈 1.57 MB, 프로젝트 목록 동영상 4.66 MB, RABBIT 2.16 MB. 영상은 자동 재생되며 포스터·명시적인 안정된 화면 비율을 보강할 여지가 있다. 모바일에서는 정적 포스터를 먼저 보여주고 영상 로드를 늦추는 방식을 검토한다. 근거: `src/app/page.tsx:14`, `src/components/common/MovieLayout.tsx:25`.
3. **RABBIT의 JS와 3D 비용.** 빌드의 First Load JS가 `/programming/rabbit` 537 kB, `/ux/rabbit` 529 kB. 첫 경로의 모바일 첫 측정 전송량은 약 9.92 MB였다. 3D 코인, 외부 HDR 환경 파일, 코드 하이라이터 등은 실제 화면 진입 시점에 로드하고 필요한 기능만 포함하는 방식을 검토한다. `RabbitCoin`은 계속 도는 Canvas와 postprocessing을 사용한다. 근거: `src/app/programming/rabbit/page.tsx:1,51`, `src/components/ux/rabbit/RabbitCoin.tsx:57,73`, 빌드·네트워크 기록.
4. **프로필 LCP 이미지가 lazy.** 이력서 첫 화면 프로필이 `loading="lazy"`로 출력된다. Next.js 15에서 이 이미지에 `priority`를 적용하고 실제 표시 폭에 맞는 `sizes`를 선언한다. 모든 이미지에 우선 로딩을 적용하지는 않는다. 근거: `src/components/resume/Resume.tsx:34`.
5. **확대 제한.** `maximumScale: 1` 때문에 전체 페이지에서 Lighthouse 접근성 항목이 실패한다. 확대 제한을 제거한다. 근거: `src/app/layout.tsx:47`.
6. **코드 블록 색 대비.** MIMO·RABBIT의 SyntaxHighlighter 테마에서 텍스트 대비 실패가 확인됐다.

## 제목 구조·공유 미리보기·구조화 데이터

- `/programming`은 H1 7개, `/ux`는 H1 10개로 한 문장을 단어 단위로 나눈다. 하나의 의미 있는 H1 아래 span으로 강조를 분리한다. 여러 H1 자체를 자동 패널티로 해석하지 않는다. 근거: 각 `page.tsx:19~23`.
- 홈 H1과 소개 제목은 `opacity: 0` 상태로 정적 HTML에 나온다. JavaScript를 끈 실제 화면에서 이름과 큰 소개 문구가 보이지 않는 것을 확인했다. 본문 소개는 읽을 수 있다. JS 오류가 나더라도 핵심 제목은 보이도록 초기 스타일을 바꾸는 것이 좋다. 근거: `src/components/home/HomeMain.tsx:66,75`, `home-nojs.png`.
- OG 이미지 메타데이터는 1200×630인데 실제 `public/profile.webp`는 **400×500**이다. 올바른 크기를 선언하거나 가로형 공유 이미지를 별도로 만든다. 페이지별 `og:url`도 없다. 근거: `src/app/layout.tsx:27` 및 이미지 실제 크기 검사.
- 12개 페이지에 JSON-LD가 없다. 홈페이지/이력서의 `ProfilePage`·`Person`, 사이트의 `WebSite`, 상세 페이지의 적절한 breadcrumb를 검토할 수 있다. 필수 색인 조건이 아니며 실제 보이는 정보와 일치해야 한다. [Google ProfilePage 지침](https://developers.google.com/search/docs/appearance/structured-data/profile-page)

## Google Search Console

`kciimnida@gmail.com` 계정에서 `seojuwon.work` 도메인 속성과 `https://www.seojuwon.work/` URL 접두어 속성이 이미 등록되어 접근 가능한 것을 확인했다. www 속성 개요는 데이터 처리 중으로 표시됐다.

도메인 속성의 사이트맵 목록은 처음에는 0개였다. 요청에 따라 **`https://www.seojuwon.work/sitemap.xml`을 제출했고, Google의 “사이트맵이 제출됨” 안내와 목록의 “성공”, 발견된 페이지 3개를 모두 확인했다.** 제출일·마지막 읽은 날짜는 2026-09-28이다. 도메인 속성은 www와 apex를 모두 포함한다.

[Search Console 사이트맵 결과](https://search.google.com/search-console/sitemaps?resource_id=sc-domain%3Aseojuwon.work)

이는 사이트맵 접수·읽기 성공이며 3개 페이지가 모두 색인되었다는 뜻은 아니다. 현재 사이트맵의 누락 경로와 canonical 문제는 그대로 수정 대상이다. 이 점검에서는 사이트 코드나 Vercel 운영 설정을 변경하지 않았다.

제출 확인 뒤 RABBIT의 URL 검사를 추가 시도했으나 전용 브라우저 창이 닫혀 조회하지 못했다. 따라서 Google 선택 canonical과 개별 페이지 색인 여부는 미확인으로 남긴다.

도메인 속성(`sc-domain:seojuwon.work`)은 DNS 확인이 필요하고, URL 접두어 속성은 계정에 맞는 HTML 메타 태그로 확인할 수 있다. 기존 확인 태그를 다른 소유자의 태그로 임의 교체해서는 안 된다. [Google 소유권 확인 절차](https://support.google.com/webmasters/answer/9008080)

## 수정 후 완료 기준

1. 공개 핵심 5개 페이지의 title/description이 고유하고 canonical과 og:url이 각각 최종 www URL을 가리킨다.
2. sitemap에 공개 대상으로 정한 페이지가 빠짐없이 들어가고, 모두 리다이렉트 없는 200·self canonical·index 상태다.
3. 미완성 페이지의 공개 정책을 정하고 링크·robots meta·sitemap을 일치시킨다.
4. www 없는 도메인과 Vercel 기본 도메인에서 최종 도메인까지 영구 리다이렉트 한 번으로 이동한다.
5. Search Console에서 소유권을 확인하고 최종 도메인의 sitemap을 제출한다. URL 검사로 사용자 지정 canonical과 Google 선택 canonical을 비교한다. 제출 직후 색인이 즉시 완료되는 것은 아니다.
6. 폰트·영상·3D를 줄인 뒤 동일 조건의 Lighthouse를 비교하고, 실제 사용자 데이터가 모이면 LCP/INP/CLS를 별도로 평가한다.

점검 범위는 기술 SEO와 공개 콘텐츠 구조다. 검색 노출·클릭·백링크·실제 Google 선택 canonical·실사용 Core Web Vitals는 해당 Search Console/측정 데이터 확인 전에는 확정하지 않는다.
