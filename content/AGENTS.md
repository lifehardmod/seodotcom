# AI 블로그 작성 규칙

## 디자인은 공통 템플릿에 고정한다

- 글마다 디자인을 만들지 않는다. AI는 frontmatter와 Markdown 본문만 작성한다.
- 페이지 배경은 사이트 상단과 이어지는 기존 검정으로 유지한다. 글 영역만 별도 배경색으로 칠하거나 상단과 본문 사이에 색 경계를 만들지 않는다. 남색·청회색을 배경이나 중립색으로 추가하지 않는다.
- 본문 폭, 글자 크기·간격, 초록 링크, 중성 회색 코드·인용·표, 오른쪽 목차는 `src/styles/blog.css`와 `src/app/blog/[slug]/page.tsx`가 담당한다. 읽기 편한 차이는 글자와 콘텐츠 블록으로 만든다.
- MDX에 import/export, JavaScript 실행식, HTML, CSS, `style`, `className`, 별도 레이아웃을 넣지 않는다. 커스텀 컴포넌트도 새로 만들지 않는다.
- 예외는 공통으로 등록된 정적 `<Image src="/blog/<slug>/image.webp" alt="내용을 설명하는 대체 텍스트" width={1200} height={630} />`뿐이다.
- H1은 frontmatter의 `title`에서 자동 출력된다. 본문은 짧은 도입 문단으로 시작하고 소제목은 `##`, 하위 제목은 `###`를 쓴다. 목차는 자동 생성되므로 본문에 직접 쓰지 않는다.
- 코드 블록에는 언어를 붙인다. 표·인용·링크·코드 복사·날짜·태그·읽기 시간·SEO는 기존 렌더러에 맡긴다.
- 다른 디자인이 필요하면 글 안에 우회 구현하지 말고 공통 UI 변경 작업으로 분리한다.

## 내용과 문체

- 한국어로, 확인된 관찰과 판단을 구체적으로 쓴다. 경험 기록이 없으면 코드·개념을 해설한다. 용어는 처음 등장할 때 필요한 만큼 풀어 쓴다.
- 제목은 독자가 얻게 될 이해나 의외의 질문을 담되, 과장된 성능·보안·사업 효과를 약속하지 않는다.
- 실제 문제나 질문에서 시작해 이를 푸는 데 필요한 순서로 쓴다. 결과·한계·교훈을 정해진 항목처럼 채우지 않는다.
- 소스 코드·공식 문서 등 원자료를 확인한다. 재구성한 코드와 가상 수치는 처음 등장하는 자리에서 예시임을 밝힌다.
- 실행하지 않은 시험, 측정하지 않은 수치, 하지 않은 작업이나 경험을 만들지 않는다. 확인할 항목은 실제 확인 결과와 구별한다.
- 독자의 이해나 판단을 바꾸지 않는 단서·반론·요약은 초안에서 지운다.
- 근거가 필요한 기술 주장에는 해당 주장을 직접 뒷받침하는 공개 원자료 링크를 붙인다. 글 끝의 참고 자료에는 실제 사용한 자료만 넣는다.
- 비공개 저장소·업무 자료가 원자료라면 공개 가능한 원리와 일반화한 예제로 설명한다. 비밀·내부 경로·공개되지 않은 이슈·운영 수치를 글에 넣지 않는다.

## 본문 이미지

- 글을 읽고 실행 흐름, 비교, 상태 변화처럼 글만으로 이해하기 어려운 곳에 이미지가 필요한지 판단한다. 도움이 되는 위치에만 생성·삽입하고 문단마다 장식 이미지를 넣지 않는다.
- 기존 글의 이미지가 있으면 시각적 기준으로 삼는다. 이 사이트의 본문 이미지는 검정·중성 회색 바탕, 읽을 수 있는 글자, 절제한 초록 강조를 사용한다. 이미지 때문에 공통 UI를 바꾸지 않는다.
- 생성한 그림은 글의 코드·설명과 맞는지 직접 확인한다. 예시 수치를 실제 측정 결과처럼 보이게 하거나, 본문이 보장하지 않는 효과를 그림으로 단정하지 않는다. 내용을 설명하는 alt를 쓴다.
- 게시용 래스터 이미지는 항상 WebP로 압축해 `public/blog/<slug>/`에 저장하고 그 파일을 본문에서 참조한다. 기본은 긴 변 최대 1600px·품질 85이며, 압축 후 실제 본문 크기에서 글자와 선이 읽히는지 확인한다. 작은 원본을 확대하지 않는다.
- 생성 도구의 PNG 원본은 도구의 원본 저장 위치에 보관한다. `public/blog/`에는 게시용 WebP만 남기고 사용하지 않는 원본·중간 시안은 쌓지 않는다. 파일 확장자만 바꾸지 않는다.
- `Image`의 width·height는 압축한 파일의 실제 크기와 맞춘다. Markdown 이미지에도 WebP 규칙을 동일하게 적용하며 `check:blog`와 빌드 검사에서 다른 형식은 거부한다.

## 작성 순서

1. 기존 대화와 원자료에서 글의 질문·실제 관찰·판단 근거를 정리한다. 경험담에 필요한 계기나 판단이 빠진 경우에만 사용자에게 묻는다.
2. `pnpm new:post <slug>`로 생성하고 메타데이터와 본문을 채운다. 기존 글은 주소를 유지한다.
3. 새 글은 `published: false`로 둔다. 발행 지시가 있어야 `true`로 바꾼다. 발행된 글을 수정한 경우 실제 `updatedAt`을 기록한다.
4. 설명에 필요한 이미지를 생성·검수하고 WebP로 압축해 삽입한다. `pnpm check:blog`를 실행한다. 필요한 정적 검사와 별도 프로덕션 빌드로 렌더링·메타데이터를 확인한다. 형식 검사를 통과해도 사실 검증은 별도로 한다.
5. 로컬 글 주소와 확인 결과, 남은 불확실성을 전달한다. 공개 저장소는 초안 파일도 푸시하면 보이므로 비공개 원자료를 쓴 초안은 공개 범위를 확인한다.

AI 규칙만으로 외부 도구의 행동까지 보장하지는 못한다. 화면 일관성은 공통 렌더러가 맡고, 금지한 MDX 문법은 `check:blog`와 빌드의 동일한 검사기로 차단한다.
