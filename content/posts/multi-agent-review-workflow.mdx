에이전트 하나에게 저장소 전체 리뷰를 맡기면 한 대화가 모든 영역의 코드를 차례로 읽으며 컨텍스트에 쌓아야 한다. 에이전트가 문제라고 판단한 내용을 반대 입장에서 따져 볼 상대도 없다.

프런트엔드 저장소 하나를 리뷰하고 고칠 때 이 일을 여러 에이전트에게 나눴다. 어떤 에이전트를 언제 띄우고 결과를 어디로 넘길지는 스크립트에 고정했고, 실행에는 Claude Code의 [dynamic workflow](https://code.claude.com/docs/en/workflows)를 썼다.

## 다음에 실행할 일은 스크립트가 정한다

Anthropic은 [에이전트 시스템을 설명하는 글](https://www.anthropic.com/research/building-effective-agents)에서 미리 정한 코드 경로로 LLM과 도구를 엮는 시스템을 workflow, LLM이 스스로 진행 과정과 도구 사용을 정하는 시스템을 agent로 나눈다. Claude Code의 dynamic workflow에서 스크립트는 Claude가 쓰지만, 실행이 시작되면 흐름을 코드가 정하므로 workflow에 해당한다. Claude가 작업에 맞는 JavaScript 스크립트를 쓰면 런타임이 이를 백그라운드에서 실행하고, [다음에 무엇을 실행할지는 스크립트가 정한다](https://code.claude.com/docs/en/workflows#when-to-use-a-workflow). 중간 결과도 대화의 컨텍스트가 아니라 스크립트 변수에 남는다.

스크립트에서 `agent()`는 서브에이전트 하나를 띄우고, `parallel()`은 여러 작업을 동시에 돌린 뒤 모두 끝날 때까지 기다리며, `pipeline()`은 목록의 항목마다 작업을 돌린다([Claude Code 문서](https://code.claude.com/docs/en/workflows#what-the-saved-script-looks-like)). `pipeline()`에 단계 함수를 여러 개 넘기면 항목마다 앞 단계가 끝나는 대로 다음 단계로 넘어가고, 다른 항목을 기다리지 않는다. 이 동작은 공개 문서가 아니라 Claude Code에 내장된 `/workflow-authoring` 스킬의 API 설명에 나온다. 반복과 분기, 작업 분배는 스크립트의 코드가 맡고, 코드를 읽고 판단해야 하는 자리에서만 에이전트를 부른다.

서브에이전트는 [새 컨텍스트에서 시작한다](https://code.claude.com/docs/en/sub-agents#what-loads-at-startup). 부모 대화의 기록이나 이미 읽은 파일을 보지 못하고, 전달받은 작업 설명에서 출발한다. 영역마다 에이전트를 따로 띄우면 다른 영역의 코드가 각 에이전트의 컨텍스트를 차지하지 않는다.

에이전트의 답은 스크립트가 다음 분기에 쓰므로 문장보다 정해진 형식의 데이터로 받는 편이 낫다. `agent()`에 `schema`를 넘기면 서브에이전트는 그 형식에 맞는 JSON을 돌려주고, 기본 설정에서는 [다섯 번 시도해도](https://code.claude.com/docs/en/workflows#what-the-saved-script-looks-like) 형식이 맞지 않으면 호출이 오류로 끝난다. 아래는 검증 결과를 받는 예시다. `verifyPrompt`는 검증 지시문을 만드는 함수를 나타낸다.

```javascript
const result = await agent(verifyPrompt(finding), {
  schema: {
    type: "object",
    required: ["verdict", "reason"],
    properties: {
      verdict: { type: "string", enum: ["confirmed", "refuted", "uncertain"] },
      reason: { type: "string" },
    },
  },
});
```

스크립트는 답변 문장을 해석하지 않고 `result.verdict` 값으로 항목을 거른다.

## 리뷰가 끝난 영역부터 검증으로 넘긴다

리뷰는 두 단계였다. 영역마다 에이전트가 코드를 읽고 문제 항목을 찾고, 찾은 항목마다 다른 에이전트가 검증한다. 두 단계를 잇는 방법은 두 가지다. 아래 예시의 `review`와 `verify`는 에이전트를 불러 결과를 돌려받는 함수를 나타낸다.

첫 번째는 모든 영역의 리뷰가 끝난 뒤 검증을 시작하는 방법이다.

```javascript
const reviews = await Promise.all(domains.map((domain) => review(domain)));
const findings = reviews.flatMap((r) => r.findings);
const verdicts = await Promise.all(findings.map((finding) => verify(finding)));
```

[`Promise.all`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Promise/all)은 넘겨받은 프로미스가 모두 이행돼야 이행된다. 첫 줄이 모든 영역을 기다리는 동기화 지점(barrier)이 되어, 일찍 끝난 영역의 항목도 가장 느린 영역의 리뷰가 끝나야 검증에 들어간다.

두 번째는 영역마다 리뷰와 검증을 이어 붙이는 방법이다.

```javascript
const verdicts = await Promise.all(
  domains.map(async (domain) => {
    const { findings } = await review(domain);
    return Promise.all(findings.map((finding) => verify(finding)));
  }),
);
```

이제 기다림은 영역 안에서만 생긴다. 예를 들어 영역 A의 리뷰가 12분, 그 항목 검증이 2분 걸리고, 영역 B의 리뷰가 3분, 검증이 8분 걸린다고 하자(설명용 수치). 동시에 실행할 수 있는 수에 제한이 없다면 첫 번째 방법은 가장 느린 리뷰와 가장 느린 검증을 더한 20분, 두 번째 방법은 영역별 합 중 큰 쪽인 14분이 걸린다. workflow는 [기본적으로 에이전트를 최대 16개(CPU가 적으면 그보다 적게)까지 동시에 실행](https://code.claude.com/docs/en/workflows#behavior-and-limits)하는데, 첫 번째 방법은 마지막 리뷰를 기다리는 동안 남는 자리를 비워 두고 두 번째 방법은 먼저 끝난 영역의 검증으로 채운다.

실제 스크립트도 영역 목록을 `pipeline()`에 넘겨, 영역마다 리뷰가 끝나면 그 영역의 항목 검증으로 이어지게 짰다. 첫 번째 모양은 다음 단계가 앞 단계의 결과 전체를 한꺼번에 봐야 할 때 필요하다. 여러 영역이 같은 문제를 중복으로 찾는다면 모두 모아 중복을 지운 뒤 검증해야 검증 횟수가 준다. 이번에는 중복 제거를 검증 뒤의 종합 단계에서 했다.

## 찾는 에이전트와 반증하는 에이전트를 나눈다

항목을 찾은 에이전트가 검증까지 하면, 처음 내린 판단을 같은 맥락 안에서 다시 확인하게 된다. 그래서 검증은 새 에이전트에게 맡겼다. 검증 에이전트는 항목을 받아 해당 코드를 직접 다시 읽고 그 지적이 틀렸다는 근거를 찾는다. 틀렸으면 `refuted`, 판단이 애매하면 `uncertain`이 아니라 `refuted`를 고르게 했다. 대신 실제 문제여도 검증 에이전트가 확신하지 못하면 기각된다.

17개 영역에서 나온 지적 가운데 약 4분의 1이 검증에서 기각됐다. 이 workflow에서 에이전트 104개가 돌았고 토큰 약 540만 개, 도구 호출 1,450회가 들었다.

검증 에이전트는 프로젝트의 전제를 모르면 틀린 지적을 확인해 줄 수 있다. 예를 들어 [React Compiler](https://react.dev/learn/react-compiler/introduction#what-should-i-do-about-usememo-usecallback-and-reactmemo)는 빌드 시점에 메모이제이션을 자동으로 적용하므로, React Compiler를 쓰는 코드에서 `useMemo`나 `React.memo`가 없다는 지적은 대개 고칠 문제가 아니다. 그래서 검증 지시문에 프로젝트가 쓰는 프레임워크 설정을 넣었다.

## 수정은 파일이 겹치지 않게 나눠 맡긴다

확인된 항목은 사람이 읽고 분류했다. 범위가 크거나 다른 작업과 조율해야 하는 항목 등은 이슈로 따로 남기고, 국소적으로 고칠 수 있는 항목만 수정으로 넘겼다. workflow는 [실행 중에 사용자 입력을 받지 않고](https://code.claude.com/docs/en/workflows#behavior-and-limits), 문서도 단계 사이에 사람의 확인이 필요하면 단계마다 workflow를 따로 돌리라고 안내한다. 리뷰와 수정도 별도 workflow로 돌리고 그 사이에 이 분류를 넣었다.

수정할 항목은 고칠 파일을 기준으로 15개 묶음으로 나눴다. 한 파일에 걸린 항목은 모두 한 에이전트가 맡고, 묶음끼리는 파일이 하나도 겹치지 않게 했다. 에이전트 15개가 같은 브랜치의 작업 트리에서 동시에 파일을 고쳤지만 한 파일을 두 에이전트가 고치는 일은 없었다. 각 에이전트는 자기 파일에 해당하는 수정만 적용하고, 테스트 실행과 git 작업은 하지 않았다. 검사는 모든 수정이 끝난 뒤 한 번에 돌렸다.

서브에이전트마다 [git worktree로 분리한 저장소 사본](https://code.claude.com/docs/en/worktrees#isolate-subagents-with-worktrees)을 주면 파일이 겹쳐도 서로 간섭하지 않는다. 다만 결과를 한 브랜치로 모으려면 사본마다 생긴 변경을 다시 합쳐야 한다. 이번 수정은 파일 단위로 나눌 수 있어서 같은 작업 트리에서 고치는 쪽을 택했다.

## 에이전트의 보고 대신 검사 결과를 본다

수정이 끝난 뒤 타입 검사, 린트, 테스트, 빌드를 돌렸다. 첫 결과에서는 타입 오류와 린트 오류가 나왔고 테스트도 여러 개 실패했다. 테스트 실패는 대부분 의도한 동작 변경 뒤에도 테스트가 이전 동작을 기대하던 경우라, 테스트를 새 동작에 맞게 고쳤다. 수정 두 건은 되돌렸다.

한 건은 가져다 쓰는 곳이 없다며 에이전트가 지운 코드였다. 실제로는 그 코드만 검사하는 테스트 파일이 있었고, 에이전트는 사용처를 찾을 때 테스트 디렉터리를 빼고 검색했다. 이 수정은 테스트 실패에서 드러났다. 다른 한 건은 난이도를 낮게 분류했던 항목인데, 고쳐 보니 요소의 의미(시맨틱)가 바뀌고 테스트에 미치는 영향도 커서 따로 다루기로 했다.

이후 타입 검사, 린트, 테스트, 빌드가 모두 통과했다. 다만 검사는 타입 오류와 기존 테스트가 잡는 회귀를 확인할 뿐, 변경이 의도에 맞는지는 판단하지 않는다.

## 종료 코드와 바이트도 확인한다

테스트는 백그라운드로 돌리면서 로그를 파일에 남기고 종료 코드를 출력하게 했다.

```bash
pnpm test > test.log 2>&1; echo "EXIT=$?"
```

Claude Code의 백그라운드 실행 도구는 이 명령이 종료 코드 0으로 끝났다고 보고했지만, 로그에는 실패한 테스트가 있었다. [Bash에서 `;`로 이은 명령](https://www.gnu.org/software/bash/manual/html_node/Lists.html)의 종료 상태는 마지막으로 실행한 명령의 종료 상태다. 여기서는 마지막의 `echo`가 성공하므로 전체 종료 상태는 0이 되고, `pnpm test`의 실제 종료 코드는 출력된 `EXIT=` 문자열에만 남는다. 종료 상태로 성패를 판단하려면 검사 명령의 종료 코드를 마지막에 그대로 돌려줘야 한다.

```bash
pnpm test > test.log 2>&1; status=$?; echo "EXIT=$status"; exit $status
```

한 수정에서는 값 여러 개를 이어 키를 만들 때 구분자로 NUL 문자를 쓰라고 지시했다. 에이전트는 이스케이프 표기 대신 실제 NUL 바이트를 소스 파일에 써 넣었다. git은 파일 앞 8,000바이트 안에 NUL 바이트가 있으면 [바이너리로 판단](https://github.com/git/git/blob/8d1b215c01512b9658d4525c54ff9b9245f9a7e8/xdiff-interface.c#L198-L204)하므로, 이 파일의 변경은 diff에 내용 없이 `Binary files ... differ`로만 표시된다. 소스 파일이 이렇게 표시되면 diff를 읽기 전에 파일 내용부터 확인해야 한다. 키를 이어 붙일 구분자가 필요하면 `JSON.stringify([a, b])`처럼 제어 문자를 쓰지 않는 방법으로 만든다.
