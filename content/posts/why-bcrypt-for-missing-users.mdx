로그인 실패 메시지를 하나로 맞춰도, 서버는 계정이 있는지 없는지 알려줄 수 있다.

계정을 못 찾았을 때 비밀번호 검증을 건너뛰는 코드가 그렇다.

로그인 실패 처리를 정리하면서 계정이 없는 경우와 비밀번호가 틀린 경우를 같이 봤다. 둘 다 401과 같은 오류 문구를 돌려주고 있었다. 응답 내용은 같았지만, 같은 배포 환경에서 기록한 응답 시간은 달랐다.

| 로그인 요청              | 상태 코드 | 응답 시간(수정 전 실측) |
| ------------------------ | --------- | ----------------------- |
| 활성 계정, 틀린 비밀번호 | 401       | 1.06~1.08초             |
| 존재하지 않는 계정       | 401       | 0.006~0.025초           |

## 검증이 생략되는 조건

실패를 반환하기까지 어떤 연산을 거치는지 조건문을 따라갔다. 계정 조회 결과와 비밀번호 검증이 하나의 `or` 조건식에 묶여 있었다. 아래는 그 조건식을 단순화한 예제다. `verify_password`는 bcrypt로 입력한 비밀번호를 검증하는 함수를 나타낸다.

```python
if (
    member is None
    or not member.enabled
    or not verify_password(candidate, member.password_digest)
):
    deny_login()
```

[Python의 `or`](https://docs.python.org/3/reference/expressions.html#boolean-operations)는 앞의 항목이 참이면 뒤를 평가하지 않는다. 계정이 없으면 `member is None`에서, 비활성이면 `not member.enabled`에서 끝나므로 `verify_password`는 호출되지 않는다. 활성 계정에 틀린 비밀번호를 넣었을 때만 bcrypt 검증 비용을 치르고 있었다. bcrypt는 비밀번호 검증에 일부러 계산 비용을 들이는 알고리즘이라, 검증을 건너뛴 경로와의 시간 차이가 크게 벌어진다.

[OWASP의 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#authentication-responses)도 계정 조회에 실패하면 일찍 반환하는 코드를 예로 든다.

bcrypt뿐 아니라 [Argon2id·scrypt·PBKDF2](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#password-hashing-algorithms) 같은 비밀번호 해싱 방식도 계정이 없다는 이유로 검증을 건너뛰면 같은 문제가 생길 수 있다. 사용하는 알고리즘이 달라도, 실제 계정과 같은 알고리즘·비용 설정의 더미 해시로 검증을 거치게 한다는 원리는 같다.

## 검증은 한 번, 해시는 재사용

먼저 계정이 없거나 비활성이어도 더미 해시로 bcrypt 검증을 거치게 했다. 더미 해시는 실제 비밀번호를 저장할 때와 같은 함수·비용 설정으로 만들었다. 기존 계정에 예전 비용 설정의 해시가 섞여 있으면 검증 비용의 차이는 남으므로 [별도의 갱신 정책](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#upgrading-the-work-factor)이 필요하다.

더미 해시를 매번 만들면 생성과 검증 비용을 둘 다 치르게 된다. 한 번 만든 값을 재사용하도록 더미 해시 함수에 캐시를 붙였다. 아래 예제의 `encode_password`와 `verify_password`는 애플리케이션의 기존 비밀번호 처리 함수를 나타낸다.

```python
from functools import cache
from secrets import token_hex


@cache
def dummy_hash():
    return encode_password(token_hex(24))


def check_credentials(member, candidate):
    can_authenticate = (
        member is not None
        and member.enabled
        and bool(member.password_digest)
    )

    digest = (
        member.password_digest
        if can_authenticate
        else dummy_hash()
    )
    matched = verify_password(candidate, digest)

    return can_authenticate and matched
```

그다음에는 활성 계정의 해시가 비어 있어도 bcrypt 없이 바로 실패한다는 걸 발견했다. 지금은 이런 계정을 만드는 경로가 없지만 모델이 허용하는 상태라, `bool(member.password_digest)`를 조건에 넣어 더미 해시를 쓰게 했다.

해시를 고른 뒤에는 `verify_password`를 항상 호출한다. 반환할 때는 `can_authenticate`도 확인하므로 더미 해시와의 비교가 일치해도 로그인을 허용하지 않는다. DB 조회나 실패 기록, 로깅에 걸리는 시간까지 같아지지는 않으므로 HTTP 응답 전체가 상수 시간으로 동작하는 것은 아니다.

계정이 없는 요청에도 bcrypt를 실행하는 만큼 서버가 처리할 연산은 늘어난다. 로그인 시도 제한을 함께 두어 이 연산이 무제한으로 반복되지 않게 해야 한다.

## 캐시를 채우는 시점도 옮겨야 한다

리뷰에서 더미 해시를 처음 쓰는 요청은 생성 비용을 한 번 더 치른다는 지적을 받았다. [`@cache`](https://docs.python.org/3/library/functools.html#functools.cache)가 값을 만드는 시점이 첫 호출이라, `encode_password`도 로그인 요청 안에서 실행되고 있었다.

서버가 요청을 받기 전에 캐시가 채워지도록 시작 훅에서 더미 해시 함수를 한 번 호출하게 바꿨다.

```python
# 각 워커가 요청을 받기 전에 실행한다.
dummy_hash()
```
