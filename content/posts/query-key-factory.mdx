TanStack Query는 서버에서 받은 데이터를 query key라는 배열로 구분해 캐시한다. 데이터를 조회하는 코드와 그 캐시를 무효화하는 코드가 같은 데이터를 가리키려면 두 곳의 배열 모양이 맞아야 한다.

프런트엔드를 새 구조로 옮기면서 서버 prefetch와 query key 규칙을 정할 때, query key는 배열을 직접 쓰지 않고 이름 붙은 factory 함수로만 만들기로 했다. factory 함수는 값을 만드는 규칙을 한 함수에 모아 두고, 호출할 때마다 그 규칙대로 새 값을 돌려주는 함수다. 아래 코드는 실제 코드를 단순화하고, 키와 데이터 이름은 일반적인 예로 바꿨다.

## 같은 데이터를 다른 키로 부르면

키를 쓰는 곳마다 배열을 직접 적으면 이런 코드가 생길 수 있다. 실제 코드가 아니라 설명을 위한 예시다.

```typescript
// 목록을 조회하는 화면
useQuery({
  queryKey: ["posts", "list", { page, search }],
  queryFn: () => fetchPosts({ page, search }),
});

// 글을 수정한 뒤 목록을 새로 받으려는 코드
queryClient.invalidateQueries({ queryKey: ["post", "list"] });
```

[TanStack Query 문서](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys#query-keys-are-hashed-deterministically)에 따르면 키 안에 있는 객체의 속성 순서는 키 비교에 영향을 주지 않지만, 배열 항목의 순서가 다르면 다른 키다. `invalidateQueries`는 [키의 앞부분이 일치하는 캐시](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation#query-matching-with-invalidatequeries)를 찾는다. 두 번째 코드의 `["post", "list"]`는 첫 번째 키의 앞부분이 아니므로 이 무효화는 목록 캐시에 닿지 않는다. 철자가 맞아도 조회 쪽이 `["posts", { page, search }, "list"]`처럼 항목 순서를 다르게 썼다면 같은 일이 생긴다.

## 키 모양을 함수 하나가 정한다

그래서 키의 모양을 정하는 함수를 공통 모듈에 두고, 키에 이름을 붙여 한 객체에 모았다.

```typescript
import type { QueryKey } from "@tanstack/react-query";

type QueryKeyParams = Readonly<
  Record<string, string | number | boolean | null | undefined>
>;

export function createQueryKeyFactory(
  namespace: string,
  resource: string,
  scope?: string,
) {
  return (params?: QueryKeyParams): QueryKey => {
    const base =
      scope === undefined ? [namespace, resource] : [namespace, resource, scope];

    return params === undefined ? base : [...base, params];
  };
}

export const queryKeys = {
  board: {
    posts: {
      list: createQueryKeyFactory("board", "posts", "list"),
    },
  },
  feed: {
    items: {
      list: createQueryKeyFactory("feed", "items", "list"),
    },
  },
} as const;
```

`createQueryKeyFactory`는 키를 바로 돌려주지 않고 키를 만드는 함수를 돌려준다. 앞쪽 항목인 영역·자원·범위는 이 함수를 만들 때 정해지고, 호출할 때 넘기는 조건 객체는 항상 맨 뒤에 붙는다. 화면 코드는 `queryKeys.board.posts.list(...)`처럼 이름으로 키를 고르므로 문자열과 순서를 다시 적을 일이 없다.

## 조건 없이 부르면 무효화 범위가 된다

검색어와 필터가 있는 목록은 조건을 모두 조건 객체로 넘긴다.

```typescript
// 검색어와 필터는 키의 마지막 객체에 들어간다.
useInfiniteQuery({
  queryKey: queryKeys.board.posts.list({ query, category, status }),
  queryFn: ({ pageParam }) =>
    fetchPosts({ query, category, status, cursor: pageParam }),
  initialPageParam: null,
  getNextPageParam: (lastPage) => lastPage.nextCursor,
});

// 글을 바꾼 뒤에는 조건 없이 부른 키로, 지금 쓰이지 않는 목록 캐시를 고른다.
queryClient.invalidateQueries({
  queryKey: queryKeys.board.posts.list(),
  type: "inactive",
});
```

`list()`는 `["board", "posts", "list"]`를, `list({ query: "react" })`는 `["board", "posts", "list", { query: "react" }]`를 만든다. 조건 객체가 항상 뒤에 붙으므로 조건 없이 부른 결과는 조건을 넣어 만든 모든 키의 앞부분이 된다. TanStack Query 문서가 더 읽을거리로 연결한 [Effective React Query Keys](https://tkdodo.eu/blog/effective-react-query-keys)도 키를 넓은 범위에서 좁은 범위 순서로 배치해, 앞부분만 넘겨 원하는 범위의 캐시를 고를 수 있게 하라고 권한다.

실제 코드에서는 항목을 추가하거나 상태를 바꾸는 요청이 성공하면 지금 보고 있는 목록 캐시를 직접 고치거나, 검색 조건이 걸려 있으면 목록을 다시 받아 온다. 화면에 없는 다른 조건의 목록 캐시는 이 키에 `type: "inactive"`를 붙여 한꺼번에 무효화한다. [쿼리 필터](https://tanstack.com/query/latest/docs/framework/react/guides/filters#query-filters)의 `type: "inactive"`는 지금 어떤 컴포넌트도 쓰고 있지 않은 캐시만 고른다. 무효화 범위를 고르려고 배열을 따로 적지 않는다.

## 키 모양에 기대는 코드가 생긴다

목록 종류(`kind`)와 선택한 항목에 따라 캐시가 여러 개 생기는 목록도 있다. 항목 하나가 갱신되면 같은 종류의 목록만 고쳐야 해서, 조건 없는 키로 고른 캐시를 [`predicate`](https://tanstack.com/query/latest/docs/framework/react/guides/filters#query-filters)로 한 번 더 거른다.

```typescript
queryClient.setQueriesData<FeedItem[]>(
  {
    queryKey: queryKeys.feed.items.list(),
    predicate: (query) => {
      const params = query.queryKey[3];

      return isRecord(params) && params.kind === kind;
    },
  },
  (current) => patchFeedList(current, updatedItem),
);
```

이 코드는 조건 객체가 키의 네 번째 자리에 있다고 가정한다. factory가 그 자리를 보장하므로 호출부마다 키를 직접 만들 때보다 믿을 수 있다. 대신 factory에서 앞쪽 항목을 하나 늘리거나 빼면 이 숫자도 함께 바꿔야 한다. 키를 만드는 곳은 한 함수로 모였지만, 그 함수의 출력 모양을 전제로 한 코드는 다른 파일에 남는다. 조건 객체가 항상 마지막에 온다는 규칙은 factory를 만들 때 단위 테스트로 고정해 두었다.

## 키에는 데이터 타입이 따라오지 않는다

목록 캐시 하나를 직접 고치는 코드는 `setQueryData<PostListData>(queryKeys.board.posts.list(params), updater)`처럼 데이터 타입을 제네릭으로 적어야 한다. 이 factory가 만드는 키에는 그 키로 저장된 데이터의 타입 정보가 없기 때문이다. [TanStack Query의 TypeScript 문서](https://tanstack.com/query/latest/docs/framework/react/typescript#typing-query-options)는 `queryOptions`로 키와 조회 함수를 함께 정의하면 반환된 `queryKey`가 조회 함수의 타입을 알고 있어서 `getQueryData`가 데이터 타입을 추론한다고 설명한다. 그렇지 않으면 제네릭을 넘기지 않는 한 결과 타입은 `unknown`이다.

```typescript
// TanStack Query의 Query Options 문서 예시를 줄여 옮겼다.
function groupOptions(id: number) {
  return queryOptions({
    queryKey: ["groups", id],
    queryFn: () => fetchGroups(id),
    staleTime: 5 * 1000,
  });
}

useQuery(groupOptions(1));
queryClient.setQueryData(groupOptions(42).queryKey, newGroups);
```

[`queryOptions`](https://tanstack.com/query/latest/docs/framework/react/guides/query-options)는 실행 시점에는 받은 객체를 그대로 돌려준다. 하는 일은 키, 조회 함수, `staleTime` 같은 옵션을 한곳에 두고 그 사이의 타입을 연결하는 것이다. 무한 스크롤 목록에는 같은 역할을 하는 `infiniteQueryOptions`가 따로 있다.

다만 여러 캐시를 한꺼번에 고르는 함수에는 이 추론이 닿지 않는다. TypeScript 문서는 `getQueriesData`에 `queryOptions`의 키를 넘겨도 타입을 추론하지 않으니 제네릭을 직접 적으라고 한다. TanStack Query 5.90.17의 [`setQueriesData` 타입](https://github.com/TanStack/query/blob/%40tanstack/query-core%405.90.17/packages/query-core/src/queryClient.ts#L211-L219)도 키에서 데이터 타입을 꺼내지 않는다. 앞의 `setQueriesData<FeedItem[]>`처럼 조건 없는 키로 여러 목록을 고치는 코드는 `queryOptions`로 바꿔도 제네릭을 계속 적어야 한다.
